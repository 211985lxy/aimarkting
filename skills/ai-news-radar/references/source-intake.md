# Source Intake Reference

Use this before implementing any customer source.

## Intake Questions

- 这个源服务谁：所有客户、单个客户、还是内部研究？
- 它补充了什么独特信号？
- 是否有稳定时间戳和 canonical URL？
- 是否能在无登录、无 cookie、无浏览器自动化下抓取？
- 是否需要 secret？缺 secret 时能否安静跳过？
- 是否会把热点/选题池灌满噪音？

Only ask the user when the answer changes public vs private routing.

## Source Classes

| Source class | Preferred integration | Default suitability |
|---|---|---|
| Official RSS/Atom | OPML or built-in source | High |
| OPML | Private customer source bundle | High private |
| Public JSON/RSS generated by GitHub/Pages | Read raw public output | High if timestamped |
| GitHub releases/commits | Atom feed | Medium |
| Public changelog/page | Focused fetch + parser | Medium |
| Newsletter archive | RSS first, stable archive second | Medium |
| X/Twitter/social account | Curated bridge or optional API | Low default |
| WeChat/Feishu/private knowledge base | Optional private bridge | Low default |
| Login-only/cookie-bound site | Skip unless explicit private integration | Avoid |

## Decision Labels

- `accept_public`: stable public source useful to most customers.
- `accept_private`: useful for one customer; keep isolated.
- `watchlist`: maybe useful, not enough signal yet.
- `needs_user_secret`: requires customer-owned token, API key, inbox, or private OPML.
- `skip`: too noisy, unstable, private, login-bound, or duplicate.

## Minimal Checks

Run the smallest relevant check:

```bash
curl -I <url>
curl -fsSL <rss-or-json-url> | head
```

For RSS/Atom, verify title, link, and published time. For pages, verify the useful content is present in server HTML before writing a parser.
